# BeanShell modules

BeanShell 3 separates the scripting runtime from its optional user interfaces and
BSF integration. All artifacts use group `org.beanshell` and the same version.

| Artifact | Features | BeanShell dependency |
| --- | --- | --- |
| `bsh` | Complete interpreter, parser, reflection, class generation, ASM, classpath management, headless commands, JSR-223 | None |
| `bsh-gui` | Swing/AWT consoles, desktop, editor, class browser, completion and GUI commands | `bsh` |
| `bsh-bsf-engine` | Apache BSF adapter | `bsh` |

For embedded scripting or `javax.script.ScriptEngineManager`, depend only on
`org.beanshell:bsh`. The core contains no BeanShell GUI, servlet, HTTP/session
server or remote client implementation. URL-based sourcing and classpath APIs
remain supported. Scripts can still use Java networking and desktop APIs when
provided by their host; this packaging change is not a sandbox.

## Running and building

Build with JDK 17 or newer using `mvn clean verify`. Published classes target Java
8. Each module writes its JAR and sources JAR to its own `target` directory.
`bsh-tests` runs distribution and OSGi integration tests and aggregates coverage
in `bsh-tests/target/site/jacoco-aggregate`; it is not installed or deployed.

The core executable now starts the text interpreter:

```sh
java -jar bsh/target/bsh-3.0.0-SNAPSHOT.jar script.bsh
java -cp 'bsh/target/bsh-3.0.0-SNAPSHOT.jar:bsh-gui/target/bsh-gui-3.0.0-SNAPSHOT.jar' bsh.gui.Console
```

Use `;` as the classpath separator on Windows. With Maven, declare optional
feature artifacts as normal dependencies; their POMs bring in core. There is no
all-inclusive default bundle or second copy of core under another artifact ID.

## API and command migration

| Old class/package | New class/package |
| --- | --- |
| `bsh.Console` | `bsh.gui.Console` |
| GUI classes in `bsh.util` | `bsh.gui` |
| `bsh.util.BeanShellBSFEngine` | `bsh.bsf.BeanShellBSFEngine` |
| `bsh.Capabilities.haveSwing()` | `bsh.gui.GuiCapabilities.haveSwing()` |

`bsh.ConsoleInterface`, `bsh.ConsoleAssignable`, `bsh.util.ValueReferenceMap`,
and scripting/JSR-223 APIs retain their names. Security guard APIs remain in
core under `bsh.security`. Each production package has a single owning module.

Adding `bsh-gui` enables `desktop`, `editor`, `classBrowser`, `browseClass`,
`makeWorkspace`, `workspaceEditor`, `fontMenu`, `frame`, `setFont`,
`setNameCompletion`, `thinBorder` and `printGuiBanner`. Core's `printBanner` is
text-only; GUI workspaces select the graphical
banner explicitly. These commands are unavailable when their modules are absent.

The legacy HTTP/session servers, remote consoles and servlet adapter were
removed upstream. They are not distributed by these modules; see the
[changelog](../CHANGES.md).

## Optional command libraries

Implement `bsh.spi.CommandProvider` with a public no-argument constructor and
return absolute command resource paths from `List<String> getCommandPaths()`.
For example, `/example/commands` contains `hello.bsh` defining `hello()`, or the
compiled command class `example.commands.hello` using BeanShell's command API.
Advertise the implementation in `META-INF/services/bsh.spi.CommandProvider`.

Provider construction and path enumeration must not evaluate scripts, open
windows or start listeners. Existing methods, explicit command imports and core
commands take precedence. Conflicting optional command names produce an error;
no provider wins by classpath ordering. Malformed registrations produce an
explanatory evaluation error when optional command discovery is needed.

BeanShell uses the explicit interpreter class loader when configured, otherwise
the thread context loader, with its defining loader as fallback. Discovered
providers contribute their loaders for command implementation classes and
resources. Discovery snapshots are interpreter/class-manager-local and reset
when loading configuration changes. As with existing scripted commands, methods
already loaded in a namespace remain there; use a fresh interpreter after
changing installed command libraries.

## OSGi

All runtime artifacts are OSGi bundles. Their manifests are generated by
`bnd-maven-plugin` from inline Bnd instructions in the module POMs. No BeanShell
bundle activator or production dependency on an OSGi mediator is required.

Core optionally requires the `osgi.serviceloader.processor` extender and zero or
more `bsh.spi.CommandProvider` capabilities. Command-provider bundles publish
`osgi.serviceloader` capabilities with explicit implementation names, `uses`
directives and an optional `osgi.serviceloader.registrar` requirement. Core also
publishes its `javax.script.ScriptEngineFactory` through the optional registrar.
All extender requirements use the version range `[1.0,2.0)`.

With a compatible mediator such as Apache Aries SPI Fly installed and wired,
command discovery crosses bundle boundaries and advertised providers are
registered as OSGi services. Core and the optional bundles can resolve and start
without the mediator. Without mediation, normal class-loader visibility rules
apply; isolated provider bundles are not automatically visible to core.

Install/start the mediator before resolving the BeanShell bundles and loading
consumer classes. If adding a mediator or providers later, refresh/re-resolve the
affected bundles and create new interpreters. Optional requirements do not imply
automatic rewiring of already resolved bundles. Service registrations follow
provider lifecycle; already cached ServiceLoader instances and scripted methods
are not a replacement for dynamic OSGi service tracking.
